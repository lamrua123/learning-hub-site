    Bài 077 — Thread và concurrent I/O

    🎯 Hôm nay học gì?

    Sau bài này, bạn có thể:

    • phân biệt tuần tự (sequential), đồng thời (concurrent) và song song (parallel);
    • hiểu thread phù hợp với công việc chờ I/O như thế nào;
    • dùng ThreadPoolExecutor với số worker có giới hạn;
    • hiểu Future, submit() và as_completed();
    • tách completion order khỏi result order;
    • chọn error policy trước khi chạy nhiều jobs;
    • tránh shared mutable state giữa workers;
    • dùng Lock khi thật sự phải bảo vệ state dùng chung;
    • không chia sẻ bừa SQLite connection hoặc object không thread-safe;
    • test concurrent workflow bằng fake I/O thay vì gọi network thật.

    Ta sẽ xây một Concurrent Endpoint Monitor:

    nhận nhiều endpoint
→ kiểm tra nhiều endpoint đồng thời
→ mỗi endpoint có timeout riêng
→ expected failure trở thành result
→ unexpected bug vẫn nổi lên
→ final report giữ đúng input order

    🧒 Hiểu cực đơn giản

    Hãy tưởng tượng bạn cần gọi điện cho bốn cửa hàng để hỏi còn hàng không.

    Cách tuần tự

    Gọi cửa hàng A
→ chờ A trả lời
→ gọi B
→ chờ B
→ gọi C
→ chờ C
→ gọi D

    Trong lúc chờ một cửa hàng nghe máy, bạn không làm cuộc gọi khác.

    Cách đồng thời

    Bốn nhân viên gọi bốn cửa hàng.

    Mỗi người dành phần lớn thời gian để chờ đầu dây bên kia.

    Tổng thời gian có thể gần với cuộc gọi chậm nhất, thay vì tổng của bốn cuộc gọi.

    Thread hữu ích với kiểu công việc:

    làm một chút
→ chờ I/O
→ làm tiếp

    Ví dụ I/O:

    • chờ network response;
    • chờ đọc file;
    • chờ ghi file;
    • chờ database server;
    • chờ thiết bị bên ngoài.

    Nhưng thêm nhiều nhân viên không tự động làm mọi việc nhanh hơn.

    Nếu tất cả cùng sửa một tờ giấy mà không có quy tắc, dữ liệu có thể hỏng.

    🧠 1. Sequential, concurrent và parallel

    Tuần tự — sequential

    Một việc hoàn tất rồi việc tiếp theo mới bắt đầu.

    A █████
       B ███
           C ████

    Đồng thời — concurrent

    Nhiều việc cùng ở trạng thái đang tiến triển trong một khoảng thời gian.

    A ██ chờ ██
B  █ chờ ███
C   ██ chờ █

    Song song — parallel

    Nhiều phần tính toán thật sự chạy cùng lúc trên nhiều execution resources.

    CPU core 1: A █████
CPU core 2: B █████

    Concurrency nói về cách tổ chức nhiều công việc đang tiến triển.

    Parallelism nói về nhiều công việc thật sự thực thi cùng lúc.

    Hai khái niệm liên quan nhưng không đồng nghĩa.

    🧠 2. Thread là gì?

    Luồng (thread) là một luồng thực thi bên trong process.

    Các threads trong cùng process thường chia sẻ:

    • memory;
    • objects;
    • module state;
    • file descriptors của process.

    Điều đó giúp truyền dữ liệu thuận tiện.

    Nhưng nó cũng tạo nguy cơ:

    nhiều threads cùng đọc/ghi một mutable object
→ kết quả phụ thuộc timing

    Timing giữa threads không ổn định.

    Không được dựa vào giả định:

    “Thread A chắc chắn chạy xong dòng này trước Thread B.”

    Trừ khi code có cơ chế đồng bộ rõ ràng.

    🧠 3. Thread phù hợp với I/O-bound work

    Công việc bị giới hạn bởi I/O (I/O-bound work) dành nhiều thời gian để chờ tài nguyên bên ngoài.

    Ví dụ:

    gửi HTTP request:      nhanh
chờ server/network:    lâu
đọc response:          nhanh

    Khi một thread đang chờ I/O, thread khác có thể tiến triển.

    Thread thường không phải lựa chọn mặc định để tăng tốc công việc nặng CPU thuần Python.

    Ví dụ CPU-bound:

    • tính toán số lượng lớn;
    • nén/biến đổi dữ liệu nặng bằng code Python;
    • duyệt thuật toán tốn CPU.

    Bài 078 sẽ học process cho CPU work và đo lợi ích thực tế.

    🧠 4. GIL ở mức cần biết

    CPython có Global Interpreter Lock — GIL.

    Ở mức của bài này, hãy nhớ:

    Nhiều Python threads không có nghĩa là nhiều đoạn Python CPU-heavy
cùng chạy song song trên nhiều cores.

    Threads vẫn rất hữu ích cho I/O vì thread chờ I/O có thể nhường cơ hội cho thread khác.

    Đừng dùng câu “Python có GIL” để kết luận threads vô dụng.

    Đừng dùng câu “threads chạy đồng thời” để kết luận CPU code chắc chắn nhanh hơn.

    Hãy phân loại workload trước.

    🧠 5. Đo baseline trước khi thêm concurrency

    Trước hết cần có phiên bản tuần tự đúng.

    def check_sequential(targets, check_function, timeout_seconds):
    results = []

    for target in targets:
        status_code = check_function(
            target.url,
            timeout_seconds,
        )
        results.append(status_code)

    return results

    Baseline giúp trả lời:

    • behavior đúng là gì?
    • output order là gì?
    • error policy hiện tại là gì?
    • concurrency có thật sự cải thiện duration không?

    Nếu phiên bản tuần tự còn sai, chạy sai đồng thời chỉ làm bug khó quan sát hơn.

    🧠 6. Vì sao cần bounded thread pool?

    Không tạo một thread cho mỗi item mà không có giới hạn.

    Nếu input có 50.000 URLs, 50.000 threads có thể làm cạn:

    • memory;
    • sockets;
    • file descriptors;
    • server capacity;
    • rate-limit budget.

    Bể thread có giới hạn (bounded thread pool) chỉ cho tối đa một số workers hoạt động.

    from concurrent.futures import ThreadPoolExecutor


with ThreadPoolExecutor(max_workers=4) as executor:
    pass

    max_workers=4 là resource policy.

    Nó không phải con số “càng lớn càng tốt”.

    Cần cân nhắc:

    • giới hạn server;
    • timeout;
    • số connections;
    • rate limit;
    • memory;
    • workload thật.

    Lưu ý: max_workers giới hạn số tasks đang chạy, nhưng nếu submit hàng triệu tasks cùng lúc thì hàng đợi chờ vẫn có thể rất lớn. Với input cực lớn, cần xử lý theo batches/chunks.

    🧠 7. submit() và Future

    future = executor.submit(
    check_function,
    target.url,
    timeout_seconds,
)

    submit() lên lịch một function call và trả về một Future.

    Future đại diện cho kết quả sẽ có trong tương lai.

    status_code = future.result()

    result():

    • trả return value khi task thành công;
    • raise lại exception xảy ra trong worker;
    • chờ nếu task chưa hoàn tất.

    Exception trong worker không biến mất.

    Nó được giữ trong Future cho tới khi caller quan sát bằng result().

    🧠 8. Submission order khác completion order

    Giả sử submit:

    A, B, C

    Thời gian:

    A: 300 ms
B:  50 ms
C: 120 ms

    Completion order có thể là:

    B, C, A

    as_completed() cho Futures theo completion order:

    from concurrent.futures import as_completed


for future in as_completed(futures):
    result = future.result()

    Completion order hữu ích để:

    • cập nhật progress sớm;
    • xử lý result ngay khi có;
    • không bị task chậm đầu danh sách chặn mọi result sau.

    Nhưng final report có thể vẫn cần input order.

    Ta phải chọn order có chủ đích.

    🧠 9. Error policy trước threads

    Khi một endpoint lỗi, app làm gì?

    Ta chọn policy:

    Expected I/O failure

    Ví dụ:

    • DNS/network unavailable;
    • connection timeout;
    • connection refused.

    Policy:

    đổi thành CheckResult state="ERROR"
→ tiếp tục endpoints khác

    HTTP response 4xx/5xx

    Server đã trả một HTTP status.

    Policy:

    đổi thành CheckResult state="DOWN"
→ giữ status code

    Unexpected programming failure

    Ví dụ checker trả sai type hoặc code có NameError.

    Policy:

    không biến thành “network error”
→ để Future raise lại
→ batch fail rõ ràng

    Nếu catch mọi Exception trong worker rồi trả ERROR, bug lập trình sẽ bị che.

    🧠 10. Shared state là nguồn bug lớn

    Code nguy hiểm:

    completed_count = 0


def worker(job):
    global completed_count
    result = do_io(job)
    completed_count += 1
    return result

    completed_count += 1 là nhiều bước logic:

    đọc value
→ tính value mới
→ ghi value mới

    Threads có thể xen kẽ giữa các bước.

    Bug do timing như vậy gọi là điều kiện tranh chấp (race condition).

    Bug có thể không xuất hiện ở mọi lần chạy.

    “Chạy thử thấy đúng” không chứng minh code thread-safe.

    🧠 11. Ưu tiên không chia sẻ mutable state

    Thiết kế an toàn hơn:

    Mỗi worker:
    nhận một immutable-ish input
    tạo result riêng
    return result

Coordinator thread:
    nhận Futures
    gom results
    cập nhật progress
    tạo report

    Trong project này:

    • worker không append vào list chung;
    • worker không tăng counter chung;
    • worker chỉ return CheckResult;
    • coordinator sở hữu dictionary kết quả.

    Loại bỏ shared mutation thường dễ hiểu hơn thêm lock ở mọi nơi.

    🧠 12. Khi thật sự cần Lock

    Khóa (lock) cho phép chỉ một thread đi vào critical section tại một thời điểm.

    from threading import Lock


counter_lock = Lock()
completed_count = 0


def record_completion():
    global completed_count

    with counter_lock:
        completed_count += 1

    Critical section là phần code truy cập shared state cần được bảo vệ như một đơn vị.

    Lock không tự làm toàn object thread-safe.

    Các lỗi thường gặp:

    • khóa khi write nhưng quên khóa khi read liên quan;
    • giữ lock trong lúc chờ network;
    • nhiều locks được lấy theo thứ tự khác nhau;
    • lock quá rộng làm mất concurrency;
    • lock che thiết kế shared state không cần thiết.

def normalize_target(target):
    if not isinstance(target, EndpointTarget):
        raise MonitorValidationError(
            "Mỗi target phải là EndpointTarget"
        )

    if type(target.name) is not str:
        raise MonitorValidationError("target.name phải là str")

    if type(target.url) is not str:
        raise MonitorValidationError("target.url phải là str")

    normalized_name = target.name.strip()
    normalized_url = target.url.strip()

    if normalized_name == "":
        raise MonitorValidationError("target.name không được rỗng")

    parsed = urlsplit(normalized_url)

    if parsed.scheme not in {"http", "https"}:
        raise MonitorValidationError("URL phải dùng http hoặc https")

    if parsed.netloc == "":
        raise MonitorValidationError("URL phải có host")

    return EndpointTarget(
        name=normalized_name,
        url=normalized_url,
    )


def classify_status(status_code):
    if type(status_code) is not int:
        raise TypeError("HTTP status phải là int")

    if status_code < 100 or status_code > 599:
        raise ValueError("HTTP status phải nằm trong 100..599")

    if 200 <= status_code < 400:
        return "UP"

    return "DOWN"


def build_report(results):
    up_count = 0
    down_count = 0
    error_count = 0

    for result in results:
        if result.state == "UP":
            up_count += 1
        elif result.state == "DOWN":
            down_count += 1
        elif result.state == "ERROR":
            error_count += 1
        else:
            raise ValueError(f"Unknown result state: {result.state}")

    return BatchReport(
        results=results,
        total_count=len(results),
        up_count=up_count,
        down_count=down_count,
        error_count=error_count,
    )

    import time
from concurrent.futures import ThreadPoolExecutor, as_completed

from monitor.domain import (
    CheckResult,
    EndpointCheckError,
    MonitorValidationError,
    build_report,
    classify_status,
    normalize_target,
)


class EndpointMonitor:
    def __init__(
        self,
        check_function,
        max_workers=4,
        timeout_seconds=3.0,
        timer_function=time.perf_counter,
        progress_function=None,
    ):
        if not callable(check_function):
            raise TypeError("check_function phải callable")

        if type(max_workers) is not int or max_workers <= 0:
            raise MonitorValidationError(
                "max_workers phải là int lớn hơn 0"
            )

        if type(timeout_seconds) not in {int, float}:
            raise MonitorValidationError(
                "timeout_seconds phải là số"
            )

        if timeout_seconds <= 0:
            raise MonitorValidationError(
                "timeout_seconds phải lớn hơn 0"
            )

        if not callable(timer_function):
            raise TypeError("timer_function phải callable")

        if progress_function is not None and not callable(
            progress_function
        ):
            raise TypeError(
                "progress_function phải callable hoặc None"
            )

        self._check = check_function
        self._max_workers = max_workers
        self._timeout_seconds = float(timeout_seconds)
        self._timer = timer_function
        self._progress = progress_function

    def _check_one(self, target):
        started = self._timer()

        try:
            status_code = self._check(
                target.url,
                self._timeout_seconds,
            )
            state = classify_status(status_code)
            error_message = ""
        except EndpointCheckError as error:
            status_code = None
            state = "ERROR"
            error_message = str(error)

        duration_ms = int((self._timer() - started) * 1000)

        if duration_ms < 0:
            raise ValueError("Monotonic timer không được đi lùi")

        return CheckResult(
            name=target.name,
            url=target.url,
            state=state,
            status_code=status_code,
            duration_ms=duration_ms,
            error=error_message,
        )

    def run(self, targets):
        if type(targets) is not list:
            raise MonitorValidationError("targets phải là list")

        selected_targets = []

        for target in targets:
            selected_targets.append(normalize_target(target))

        if not selected_targets:
            return build_report([])

        worker_count = min(
            self._max_workers,
            len(selected_targets),
        )
        results_by_index = {}
        completed_count = 0

        with ThreadPoolExecutor(
            max_workers=worker_count,
            thread_name_prefix="endpoint-check",
        ) as executor:
            future_to_index = {}

            for index, target in enumerate(selected_targets):
                future = executor.submit(self._check_one, target)
                future_to_index[future] = index

            for future in as_completed(future_to_index):
                index = future_to_index[future]
                result = future.result()
                results_by_index[index] = result
                completed_count += 1

                if self._progress is not None:
                    self._progress(
                        completed_count,
                        len(selected_targets),
                        result,
                    )

        ordered_results = []

        for index in range(len(selected_targets)):
            ordered_results.append(results_by_index[index])

        return build_report(ordered_results)

    Quan sát hai ownership khác nhau:

    workers:
    gọi I/O
    tạo CheckResult riêng

coordinator:
    sở hữu results_by_index
    tăng completed_count
    gọi progress callback
    tạo final order

    progress_function chạy ở thread gọi run(), không chạy trong worker.

from urllib.request import Request, urlopen

from monitor.domain import EndpointCheckError


def check_http_status(url, timeout_seconds):
    request = Request(
        url,
        method="GET",
        headers={"User-Agent": "EndpointMonitor/1.0"},
    )

    try:
        with urlopen(
            request,
            timeout=timeout_seconds,
        ) as response:
            return response.status
    except HTTPError as error:
        return error.code
    except (URLError, TimeoutError, OSError) as error:
        raise EndpointCheckError(
            "Không thể kết nối endpoint"
        ) from error

class ConcurrencyProbe:

        self._lock = Lock()
        self.active_count = 0
        self.max_active_count = 0

    🧠 26. Timeout và cancellation thực sự có nghĩa gì?

    Per-operation timeout

    urlopen(request, timeout=2.0)

    Giới hạn việc chờ của network operation theo contract của adapter.

    Mỗi I/O operation nên có timeout hữu hạn.

    future.cancel()

    cancel() có thể hủy task chưa bắt đầu.

    Nó không phải nút “giết thread” an toàn.

    Nếu worker đang chạy blocking call, cancel() thường không dừng call đó ngay.

    Executor context manager

    with ThreadPoolExecutor(...) as executor:
    ...

    Khi rời with, executor shutdown và chờ running tasks hoàn tất.

    Vì vậy timeout phải được thiết kế tại I/O boundary, không chỉ kỳ vọng shutdown sẽ dừng mọi blocking operation.

    B — không

    try:
    status = check(url)
except Exception:
    return CheckResult(state="ERROR")

    NameError và contract bug bị che thành network error.

    Bug 5 — shared counter không lock

    completed_count += 1

    Nhiều workers cùng thực hiện. Một lần chạy đúng có đủ bằng chứng không?

    Bug 6 — lock quanh network call

    with lock:
    result = fetch(url)

    Concurrency thực tế còn lại bao nhiêu?

    Bug 7 — dùng chung SQLite connection

    future = executor.submit(
    write_post,
    shared_connection,
    post,
)

    Ai sở hữu transaction? Connection có thread-safe theo contract không?

    Bug 8 — không có timeout

    urlopen(request)

    Một worker có thể chờ bao lâu? Executor shutdown phải chờ điều gì?

    Bug 9 — fake không thread-safe

    class FakeChecker:
    def __call__(self, url, timeout):
        self.calls.append(url)
        return self.responses.pop(0)

    Response nào thuộc URL nào khi call order không ổn định?

    Hãy map response theo URL thay vì pop theo timing.

    Bug 10 — validate trong worker

    Target thứ năm invalid, nhưng bốn workers đầu đã gửi requests.

    Batch có còn “không side effect khi input invalid” không?

    Bug 11 — cancel() được hiểu là kill

    Task đã chạy network call.

    future.cancel() trả False nhưng code vẫn báo “đã hủy”.

    Bug 12 — update Tkinter từ worker

    Worker gọi:

    status_label.config(text="Done")

    UI toolkit có cho phép gọi widget từ worker thread không? Boundary nào nên schedule UI update?

    📌 36. Thuật ngữ quan trọng

    • tuần tự (sequential): công việc trước hoàn tất rồi công việc sau mới bắt đầu.
    • đồng thời (concurrent): nhiều công việc cùng tiến triển trong một khoảng thời gian.
    • song song (parallel): nhiều phần tính toán thực sự chạy cùng lúc.
    • luồng (thread): luồng thực thi bên trong một process và chia sẻ memory với các threads khác.
    • I/O-bound work: workload chủ yếu bị giới hạn bởi thời gian chờ input/output.
    • CPU-bound work: workload chủ yếu bị giới hạn bởi thời gian tính toán CPU.
    • GIL (Global Interpreter Lock): cơ chế của CPython ảnh hưởng cách Python bytecode chạy giữa threads.
    • thread pool: nhóm worker threads được tái sử dụng để chạy nhiều tasks.
    • worker: thread/process nhận và thực hiện một task.
    • worker budget: số workers tối đa được policy cho phép hoạt động.
    • Future: object đại diện cho result hoặc exception sẽ có sau.
    • submission order: thứ tự tasks được đưa vào executor.
    • completion order: thứ tự tasks hoàn tất.
    • shared mutable state: dữ liệu có thể thay đổi và được nhiều threads cùng truy cập.
    • race condition: kết quả phụ thuộc vào timing xen kẽ giữa các operations.
    • thread-safe: giữ contract đúng khi được dùng đồng thời theo phạm vi đã công bố.
    • Lock: cơ chế cho một thread tại một thời điểm đi vào critical section.
    • critical section: đoạn code truy cập shared state cần được bảo vệ như một đơn vị.
    • per-operation timeout: giới hạn chờ cho một I/O operation.
    • cancellation: yêu cầu task chưa chạy không bắt đầu hoặc task hợp tác dừng theo policy.
    • coordinator: phần điều phối submit, nhận Futures, gom results và tạo report.

    ✅ Điều cần nhớ

    Threads phù hợp với waiting-heavy I/O, không phải nút tăng tốc mọi workload.

    Bound workers; đừng tạo một thread không giới hạn cho mỗi item.

    Workers return riêng; coordinator gom results và sở hữu shared state.

    Completion order phục vụ progress; input order có thể phục vụ final report.

    Expected I/O failure là result; unexpected programming bug phải nổi lên.

    Không chia sẻ bừa SQLite connection, file handle hoặc UI widget giữa threads.
